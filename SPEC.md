## 0. Product in one paragraph

ZeroGap is a web app for Indian small businesses and their CAs. Upload sales bills → AI reads them, checks HSN codes and GST rates, and generates a portal-ready GSTR-1 return file. Upload purchase bills + GSTR-2B → finds tax credit you're losing or wrongly claiming, in rupees. One triangle screen checks GSTR-1 vs 2B vs 3B agree before you pay tax. Monthly, quarterly, yearly views. Every problem explained in plain words, never tax jargon. The whole product is designed to feel **stress-free**: no dead ends, no jargon, every number explained, demo data in one click.

## 2. Government process bible (read before writing any tax logic)

### 2.1 The three returns
- **GSTR-1** — outward supplies (your sales), filed by the **11th** of next month. Invoice-level for B2B.
- **GSTR-2B** — auto-generated by GSTN around the **14th**; the **legal ceiling** on input tax credit (Sec 16(2)(aa), Rule 36(4)). You cannot claim credit for what isn't in 2B.
- **GSTR-3B** — summary return + actual tax payment, filed by the **20th**.
- **IMS (Invoice Management System)** — mandatory since Apr 2026: recipient must Accept / Reject / Keep-pending each supplier invoice; 2B is built from accepted invoices.

### 2.2 Auto-notices (why Features 2 & 3 exist)
- **Rule 88C → DRC-01B:** system compares GSTR-1 liability vs 3B paid. Gap → notice.
- **Rule 88D → DRC-01C:** system compares 3B ITC claimed vs 2B available. Excess → **7-day** deadline to pay or explain invoice-by-invoice, else next GSTR-1 is **blocked**.
- Product rule: we **flag gaps + list legitimate causes**, never declare "this is wrong" (§2.6).

### 2.3 GSTR-1 sections we generate (v1)
| Section | Tables | Content |
|---|---|---|
| B2B | 4A, 4B, 4C | Registered customers, invoice-level |
| B2C Large | 5A, 5B | Unregistered + inter-state + invoice value above threshold |
| B2C Others | 7 | Rate-wise consolidated totals (not invoice-level) |
| Credit/Debit notes | 9A, 9B | Against original invoices |
| Nil/exempt/non-GST | 8A–8D | Consolidated |
| HSN summary | 12 (12A B2B / 12B B2C tabs since May 2025) | Per-HSN totals; **mandatory for B2B** |
| Documents issued | 13 | Bill serial ranges, cancelled count |

### 2.4 GSTR-1 JSON schema (offline-tool format — generate EXACTLY this)
```json
{
  "gstin": "06ABCDE1234F1Z5",
  "fp": "092026",
  "gt": 1234567.89,
  "b2b": [{
    "ctin": "07ABCDE1234F1Z5",
    "inv": [{
      "inum": "INV-001", "idt": "15-09-2026", "val": 11800,
      "pos": "07", "rchrg": "N", "inv_typ": "R",
      "itms": [{ "num": 1,
        "itm_det": { "rt": 18, "txval": 10000, "iamt": 0, "camt": 900, "samt": 900, "csamt": 0 } }]
    }]
  }],
  "b2cl": [],
  "b2cs": [],
  "hsn": { "data": [{
    "hsn_sc": "8471", "desc": "Computers", "uqc": "NOS", "qty": 10,
    "txval": 100000, "iamt": 0, "camt": 9000, "samt": 9000, "csamt": 0
  }]}
}
```
Field notes: `ctin` = customer GSTIN · `idt` = DD-MM-YYYY · `pos` = 2-digit state code (first 2 digits of counterparty GSTIN) · `rchrg` = Y/N · `inv_typ` = R (regular; v1 only) · `rt` = GST rate % · `txval` = taxable value · `iamt/camt/samt/csamt` = IGST/CGST/SGST/cess. Inter-state ⇒ `iamt` only; intra-state ⇒ `camt`+`samt` split. `fp` = MMYYYY.

### 2.5 Invoice auto-classification (Feature 1)
1. Customer GSTIN present → **B2B**
2. No GSTIN + inter-state + invoice value > threshold → **B2CL** (threshold was ₹2.5L; verify current notification before freezing)
3. Everything else B2C → **B2CS** (aggregated per state × rate)

### 2.6 Validation rules (run on every invoice; block export until fixed or acknowledged)
- GSTIN format: `/^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z]{1}[1-9A-Z]{1}Z[0-9A-Z]{1}$/`
- Tax arithmetic: `round(txval × rt/100) == iamt + camt + samt` within **±0.01**
- Date strictly `DD-MM-YYYY`, within the filing period
- HSN: 4–8 digits; digit rule — turnover ≤ ₹5cr ⇒ min **4 digits**, > ₹5cr ⇒ min **6 digits**
- HSN exists in `hsn_master`; billed rate == master rate for that HSN → else flag `RATE_MISMATCH` (advisory, not blocking — some HSNs have conditional rates)
- Invoice number unique per GSTIN + period

### 2.7 HSN master (reference data we bundle)
`hsn_code → { description, gst_rate, conditions? }`. Source: CBIC rate schedules (snapshot at build time; show "rates as of <date>" in UI). Conditional-rate HSNs flagged `verify_manually: true`.

### 2.8 Mismatch taxonomy (Feature 2 — the CA-approved cause list)
`SUPPLIER_NOT_FILED` · `SUPPLIER_FILED_LATE` · `WRONG_GSTIN` · `VALUE_MISMATCH` · `CREDIT_NOTE_PENDING` · `INELIGIBLE_17_5` · `DUPLICATE_BOOKING` · `PERIOD_SHIFT` · `IMPORT_RCM` (verify via Bill of Entry, not 2B). Each cause maps to a plain-language explanation template + recommended action.

| Layer | Choice | Why (latency-first reasoning) |

| Frontend | **Next.js 15 App Router + React + Tailwind v4** | One codebase, SSR fast first paint, fastest to build well in 3 weeks |

| Hosting | **Cloud Run**, `asia-south1` (Mumbai) | GCP requirement; Mumbai = closest to users; scale-to-zero |
| DB (transactional) | **Firestore** Native mode, `asia-south1` | Single-digit-ms doc reads, serverless, document model fits invoices |
| DB (analytical) | **BigQuery**, `asia-south1` | Quarterly/yearly rollups (Feature 4); dual-write from ingestion |

**Why not Cloud SQL:** connection management + ops overhead + higher p99 for simple doc reads. Firestore wins for this workload.
**Why not a separate backend service:** 3-week budget; API routes on the same Cloud Run service keep deploys to one command.
**Single-region rule:** EVERYTHING in `asia-south1`. No cross-region hop anywhere — this is the #1 latency decision.

## 6. Database design

### 6.1 Firestore (primary — all reads served from here)
```
users/{uid}                          { email, name, createdAt }
businesses/{bizId}                   { name, gstin, turnoverSlab: 'UNDER_5CR'|'OVER_5CR',
                                       stateCode, ownerUid, createdAt }
businesses/{bizId}/periods/{yyyymm}  { status: {f1,f2,f3},           // 'idle'|'processing'|'done'
                                       totals: { salesTxval, salesTax, purchaseTxval,
                                                 itcAvailable2B, itcClaimed },
                                       triangle: { liabilityGap, itcGap },
                                       moneyAtRisk, matchScore, updatedAt }   // ← dashboard = 1 read
businesses/{bizId}/periods/{yyyymm}/salesInvoices/{invId}
  { inum, idt, ctin, ctinName, pos, rchrg:'N', invTyp:'R', section:'B2B'|'B2CL'|'B2CS',
    items:[{hsn, qty, uqc, txval, rt, iamt, camt, samt}], totals:{...},
    hsnFlags:[{hsn, issue:'MISSING'|'INVALID'|'RATE_MISMATCH', expectedRate}],
    source:{storagePath, docAiConfidence}, correctedByUser:bool, createdAt }
businesses/{bizId}/periods/{yyyymm}/purchaseInvoices/{invId}   // same shape, supplier side
businesses/{bizId}/periods/{yyyymm}/gstr2b/{recId}
  { supplierGstin, inum, idt, txval, iamt, camt, samt, source:'UPLOAD' }
businesses/{bizId}/periods/{yyyymm}/reco/{recId}
  { kind:'PURCHASE_2B', purchaseInvId, gstr2bId|null,
    status:'MATCHED'|'MISMATCH'|'MISSING_IN_2B'|'MISSING_IN_BOOKS',
    cause:'SUPPLIER_NOT_FILED'|..., amountAtRisk, explanation, action }
reference/hsnMaster/{hsn}            { desc, rate, verifyManually:bool, updatedAsOf }
jobs/{jobId}                         { type, bizId, period, status, progress, error }
```

### 6.2 BigQuery (analytics mirror — powers Feature 4)
Dataset `gst`, tables partitioned by `period`: `sales_invoices`, `purchase_invoices`, `gstr2b_records`, `reco_results` — same fields as Firestore, flat. Quarterly/yearly = `SUM … GROUP BY` queries; results cached back into `periods` docs (`rollups: { q: {...}, y: {...} }`).

### 6.3 Period-aware from day one
Every invoice, 2B record, and result carries `period: 'YYYY-MM'`. Feature 4 is then pure aggregation — no rework later.

## 7. API design (Next.js route handlers — all validated with zod)

| Method | Route | Behaviour |
|---|---|---|
| POST | `/api/businesses` | Create business `{name, gstin, turnoverSlab, stateCode}` → `{bizId}` |
| GET | `/api/businesses` | List user's businesses |
| POST | `/api/uploads` | `{bizId, period, kind:'sales'&#124;'purchase'&#124;'gstr2b', files[]}` → **202** `{jobId}`; files → Storage `raw/{bizId}/{period}/{kind}/` |
| GET | `/api/jobs/:id` | `{status, progress, error}` (UI prefers Firestore `onSnapshot`) |
| GET | `/api/invoices?bizId&period&kind&section` | Paginated (pageSize from config), filterable by section/status |
| PATCH | `/api/invoices/:id` | User corrections `{fields}` → re-validate, re-classify, mark `correctedByUser`, refresh period snapshot |
| POST | `/api/reconcile` | `{bizId, period}` → runs Feature 2 + 3 engines → **202** `{jobId}` |
| GET | `/api/dashboard?bizId&period` | Returns the denormalised `periods/{yyyymm}` doc (1 read) |
| POST | `/api/explain` | `{mismatchIds[]}` → **SSE stream** of Gemini plain-language cards |
| GET | `/api/gstr1/export?bizId&period&format=json&#124;xlsx` | Validates (§2.6: blocks on errors, warns on advisories), then downloads `GSTR1_{GSTIN}_{MMYYYY}.json` / Excel workbook |
| GET | `/api/reports?bizId&period&granularity=month&#124;quarter&#124;year` | Feature 4 rollups (BigQuery, cached in Firestore) |

**Error contract:** `{ error: { code, message } }` — codes: `VALIDATION_FAILED`, `JOB_FAILED`, `NOT_FOUND`, `RATE_LIMITED`, `UNAUTHENTICATED`. Messages are plain-English, never stack traces.

## 8. Latency playbook (the "very very less latency" section)

1. **Single region** (`asia-south1`) for Cloud Run, Firestore, BigQuery, Document AI, Vertex AI, Storage. No cross-region calls, ever.
2. **Dashboard = 1 Firestore read.** The `periods/{yyyymm}` doc is precomputed on every write; the dashboard never aggregates on the fly.
3. **Async slow work.** Document AI (2–8s/doc), reconciliation, exports → jobs with progress. UI never waits; `onSnapshot` pushes completion.
4. **Streaming AI.** Gemini Flash over SSE — first token ≈1s, perceived instant. Never block a page on a full completion.
5. **Optimistic UI.** Corrections apply instantly locally, then sync; skeletons on every route; no blank screens.
6. **Pagination + virtualisation.** Invoice lists at pageSize (config); dashboard charts aggregate server-side.
7. **Image handling.** Thumbnails for previews; lazy-load; `next/image` with Storage signed URLs.
8. **BigQuery only for rollups.** Monthly screens read Firestore; quarterly/yearly hit BigQuery with results cached into Firestore (`rollups`).
9. **Cold starts.** Cloud Run `min-instances: 1` during demo week only (costs paise, kills cold start on stage).
10. **Budgets (config):** p95 dashboard < 800ms · explanation first-token < 1.5s · upload accept < 300ms. Log violations; fix before adding features.

### 9.2 Stress-free UX principles (non-negotiable — the builder must follow all ten)
1. **No dead ends.** Every empty state shows an illustration, one sentence, and a button (usually "Load demo data" or "Upload bills").
2. **No jargon.** Words like "ITC", "B2B", "HSN" always get a `?` tooltip in plain words on first appearance per screen.
3. **Never lose work.** Corrections autosave; uploads resume as jobs; drafts survive refresh.
4. **Always show progress.** Every job shows a progress bar + per-file status. Nothing happens silently.
5. **Confirm destruction.** Delete actions need a typed or double-click confirm.
6. **One primary action per screen.** The amber button is always the obvious next step.
7. **Forgiving inputs.** Accept `15/9/26`, `15-09-2026`, `15 Sep 2026` — normalise silently. Trim spaces in GSTIN, auto-uppercase.
8. **Explain every number.** Every ₹ figure has a "Why?" affordance (hover/click) showing the 1–2 line math behind it. Builds trust with CAs.
9. **Celebrate clean states.** Zero issues = full-width emerald "All clear ✓" moment, not an empty table.
10. **Five clicks to value.** Landing → demo → result in ≤ 5 clicks. Count them in QA.
